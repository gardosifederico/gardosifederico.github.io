Home NAS

Concerning the everyday more frequent threats to personal data stored on big cloud servers, I have decided to create my own home-NAS to have a safe and easy-to-manage system where to store documents and pictures.

Design Objectives

- The System shall be accessible with username and permissions.
- The System shall be accessible outside of the home LAN, without using Port Forwarding.
- The System shall be constantly monitored (Temperature and CPU load).
- The Monitoring System shall be capable of provising notifications in case of over temperature, or overloading.
- The Monitoring System shall monitor with low frequency the available NAS Volume.
- The System shall be easily updatable to bigger storages without losing stored data.
- The System shall provide automated Back Ups in different HW memories.
- The System shall provide RAID storage with back up integrated (RAID 1).

HW Architecture

- Rasperry PI 4, 8GB RAM
- 2x Hard-Drive 1 TB
- 2x Hard-Drive 500 GB
- Powered USB Hub

Raspberry Pi 4 (8GB RAM) has been selected only because of availability. Lower RAM also allows for NAS to run flawlessly, Pi 4, nontheless, is very good for temperature management (Pi 5 heats up much faster with respect to Pi 4).

The Hard-Drive also have been chose for their availability, some old memories were calling for some utilization.

Powered USB Hub is needed to avoid Under-Current: by plugging 4 memories to the Pi, the Pi needed to supply more current than possible to load the memories. With the Powered USB the memories can run autonomously, and Pi does not need to provide current to them.

SW Architecture

- DebianOS (for the Pi 4)
- mdadm
- rsync
- Samba
- Tailscale
- nginx
mdadm allows to create and mount the real RAID (type 1) based on the memories specified in the configuration. The chose Architecture is to use the 2x 1TB memories in RAID: RAID 1 means that the allowable NAS memory storage availability will be 1 TB, each memory will be to store the same file in same path (redundancy).

rsync is instead used for backing up the files in the back up memories (2x 500GB). when the 500GB memory will be exceeded it will be possible to replace them.

Samba is the SW used to create access to the NAS with a Username and Password to perform the classic operations of file transfer.

nginx is used to enable local website at the IP Address of the Pi, that is used to display the plots related to the healt status of the Pi

Automations & Operations


Use of NAS outside of Home Network

To access the NAS services from outside the home network, Tailscale is used. Tailscale allows to create a mesh network between a limited number of devices, that can be accessed using a local IP address when activated.

Replenishment Strategy

In case of Memory HW Failure: RAID 1 can continue operating without knowing which HW is failed. mdadm will allow me to know which is the defect HW and it can be replaced with a new memory of the same size.

Monitoring

Through Cron Jobs, every minute the Temperature and the CPU Load are monitored and logged in a .log file.
The .log file is read to perform the temperature and CPU Load Plots, and it is also archived on a dedicated folder of the NAS every Week (with indication of the Calendar week of generation). In this way the PI memory is not impacted by the size of the .log file. The archive is performed with dedicated Cron Job the first minute of each Week.
Based on the values read in the .log file a telegram bot is also used to communicate the health status of the Pi:
- Everyday 12.00 CEST the routine communication if no monitoring issue to reports
- If temperature goes above 55 Celsius immediate communication of Temperature issue via telegram
- If temperature goes back below 55 Celsius within 5 minutes another communication of issue resolved sent via telegram
- Telegram bot can perform reboot operations and request specific healt status figures of merit to help me debug the issue from the distance
- If CPU load goes above 10% also a monitoring alert is raised from the Telegram Bot
